# EXP-COMPRESSION-001 · Lossless Stockfish compression

**Reported observation, pending reproduction.** The owner reported a possible size reduction from 135 MB to 88 MB for Stockfish 19. The exact input, units, original archive and codec settings from that observation are unknown. The owner identifies MSZIP and recalls direct GUI and custom HTML use. Size reduction, runtime gains and Elo gains are separate outcomes. The original was not recovered. Independent gzip and xz trials and a native MSZIP launcher reconstruction are complete. [Recovery scope, measurements and decision](../results/EXP-COMPRESSION-001/README.md)

## Seven research questions

1. **What was compressed?** Inspect the container magic, archive member list and uncompressed member lengths, executable sections and `EvalFile` configuration. Identify the executable, embedded or external network, or another input such as an archive containing both source and engine. Hash archive and members separately. For each variant report input bytes, compressed payload bytes, total shipped bytes (including decoder and metadata), installed bytes, compression ratio and percent saved. Disclose stripping and any architecture differences.
2. **Can the original be recovered bit for bit?** Preserve the original read-only. For the first packaging trial, pin a lossless codec and flags, for example Zstandard level 3 with one worker. Compress the exact identified file, decode to a separate output, run `cmp` and compare independent full SHA-256 digests and byte counts. Archive manifests, including executable mode where relevant. A matching bench cannot substitute for this byte comparison. For an integrated loader, independently verify the exact reconstructed serialized NNUE stream against the supplied original before testing search.
3. **Does resident memory change?** On a quiescent, dedicated worker, use identical hash, threads, NNUE sharing and NUMA policy. Sample process and decoder memory before loading, after readiness, after first search and during sustained search. Record peak RSS with GNU time and RSS/PSS/private and shared pages from `/proc/PID/smaps_rollup`. With multiple processes, report group peak and total PSS so shared network pages are accounted for once. Report decoder buffers, temporary file sizes and page faults separately.
4. **Does hardware cache behavior change?** Pin to the same cores. Record CPU model, microcode, kernel, affinity, frequency policy and actual available PMU events. Collect cycles, instructions, cache references/misses and, where supported, explicit L1D and LLC load/access/miss events separately for load and steady-state search. Report miss rates and misses per fixed million searched nodes, event coverage and multiplexing. File-page cache and CPU caches are different measurements. If PMU access is unavailable, mark this question unmeasured.
5. **What does decompression cost?** Time decode alone and the end-to-end launch path, including child processes and temporary I/O. Use a monotonic clock from process start to `uciok`, to `readyok`, and to the first completed fixed-node `bestmove`. Some resources are loaded lazily. Capture wall and user/system CPU time, CPU utilization, bytes read/written and peak memory. Separate one-time install/unpack costs from per-launch or recurring decoder work. Alternate baseline and candidate order across at least ten paired trials per cache condition when the budget allows. Warm means a fresh process after a priming read/run. Cold means a fresh disposable VM/image or controlled eviction of the relevant file pages with residency verified. Record shared-memory state and first-run versus repeat behavior for both. Leave the cold result unavailable if the runner cannot establish that condition.
6. **Does steady-state NPS change?** After warmup, run the same fixed-node position suite on a warmed engine, with the same compiler/ISA, network, search settings and affinity. Reset hash identically between trials. Record per-trial completed nodes, elapsed search time, NPS, best moves, scores and bench signature. Interleave A/B and B/A blocks on an idle worker. Report paired NPS ratios and an uncertainty interval with its method, sample size and raw observations. A ratio whose interval crosses 1 is inconclusive for speed. Startup latency has its own denominator.
7. **Is there a measurable strength effect?** An install-only archive that restores the identical executable and network has no changed engine to screen. Archive the packaging result. If a runtime path changes per-move cost or usable working memory and the first six questions establish correctness and a repeatable plausible benefit, request independent review and run a bounded, predeclared clock-based paired match. Preserve complete PGNs, opening seed and checksum, settings, W/D/L, pentanomial counts and the paired Elo interval. Use longer controls and official sequential Fishtest evidence where applicable under the promotion policy. Label insufficient evidence inconclusive. A useful packaging or latency result can be reported on its own.

## Ownership and execution order

- The search and evaluation researchers identify the file and codec, inspect existing packaging and network layout, and record why the proposed pipeline might affect runtime. Distinguish transport-only compression, decode-on-load and an inference representation that would have to be decoded repeatedly. Each is a separate experiment.
- The implementation agent uses a dedicated cloud worktree and experiment branch at the pinned baseline for the standalone packaging trial. Write to an isolated output directory. Pursue an integrated loader only as a separately identified comparison if the measured mechanism warrants it. Preserve the original executable, network and release files.
- The [statistical testing agent responsible for performance measurements](../agents/performance.md) preregisters resource limits and runs the timing, memory and cache measurements. Store commands, tool versions, file hashes, raw trial observations, units and uncertainties under the experiment ID. Publish small manifests and reports in Git and retain large artifacts by checksum.
- The independent reviewer checks scope, provenance and fair conditions. The testing agent verifies bit identity, normal UCI startup, actual network load, deterministic single-thread search and upstream correctness tests before allocating games. The coordinator records each result and its limitations, including failures, then applies the promotion policy.

Research runs use cloud/GitHub workers. The owner's optional 8-core, 16 GB machine is descriptive capacity. Leave OS headroom if a local run is later requested. For either host, enforce the lower of the configured job limit and measured available CPU/RAM. Serialize comparison trials, log actual CPU time and wall time, and stop at the approved budget. Record an isolated packaging trial separately from engine work. Engine integration, a match and upstream submission follow the later phase gates.
